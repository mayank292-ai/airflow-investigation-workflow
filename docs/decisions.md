# Decision records

Each choice below states its current limits and a reason to revisit it.

| Requirement | Alternatives and choice | Reason / limitation / revisit trigger |
|---|---|---|
| Unfamiliar failures | Agent rather than fixed scenario rules | Tool selection can follow unexpected logs/helpers; interpretation can be wrong. Revisit with recorded failures and deterministic review. |
| Evidence collection | Typed tools rather than copying into chat | Keeps identity, provenance and access limits consistent. Missing integrations limit diagnosis. Add adapters when real evidence requires them. |
| Framework | `create_agent` rather than Deep Agents or custom graph | Current supported API already gives tools, structured output and middleware. Deep Agents offers filesystem/context facilities that would require extra capability controls here. A custom graph adds no concrete benefit yet. Revisit when measured context limits or explicit human gates need it. |
| Compact runtime | One agent | No demonstrated parallel specialist need; multiple agents would complicate evidence ownership and budget. Revisit after evaluation shows a specific bottleneck. |
| Model/cost | OpenAI GPT-5.4 mini, configurable | Tool calling and structured responses with documented pricing; live access tested. Default local authorization is$3; user subsequently approved$15 total here. Conservative retry reservations and prior entries are preserved. No silent model upgrade. Revisit only with pricing, access and repeated evaluation. |
| Tools | Direct LangChain Python tools rather than MCP | One local runtime does not need a protocol server. MCP is useful later for reuse across clients, not an architectural badge. |
| Source navigation | Literal search and AST rather than vectors | Small content-addressed snapshots make bounded exact retrieval understandable. No embedding infrastructure or whole-program analysis. Revisit if measured larger source sets defeat this approach. |
| Deployment | Local CLI and existing Airflow UI | Matches engineering workflow and interview constraints. No frontend/hosting. Revisit only after utility and reliability are demonstrated. |
| Persistence | PostgreSQL for Airflow; separate SQLite records/checkpoints | Uses supported metadata storage and compact host workflow storage. SQLite concurrency/resume limits remain explicit. Revisit with concurrent operational demand. |
| Source alignment | Per-deployment manifest + run binding | Avoids treating current branch as executed source. Runtime infrastructure hash is recorded but that private implementation is not inspectable by the model. Revisit with Git/image/DAG-version integrations. |
| Remediation | Patch only on explicit request | Initial report remains focused on evidence and assumptions. Generated edits are isolated and never deployed automatically. Revisit after useful validation and approval gates exist. |
| Recovery | Exclude automatic production recovery | No production access, business preconditions or post-action proof exists. A future human-approved action needs bounded permissions, prechecks and verification. |
| Airflow version | Pin 3.3.1 API/image rather than mix versions | Adapter follows that version's official OpenAPI spec. A newer patch release exists; updating requires compatibility/security review and rerunning real integrations, rather than silently changing the supported version. |
| Demo trigger | Future bounded scheduled history | Preserves genuine execution, supports fresh investigations without reruns. Scheduler time and external interruptions can affect preparation. Existing history is never rewritten to look scheduled. |
| Follow-up context | Same-investigation handoff plus bounded recent source retention | Live continuations first hit context admission, then erased useful source through coarse clearing. Keep persisted history, edit only request copies, and retain up to four source ranges / 24 KB. Review showed that completion alone did not prove useful reasoning. Revisit with larger snapshots and repeated evaluations. |
| Limit exhaustion | Reject excess tools, reserve final output and optional correction | A live continuation exceeded24 requested tools. Continue-mode errors permit bounded output. Operations with >=6 calls reserve two final slots; short evaluations reserve one. Coverage hints prioritize material uninspected evidence in the last retrieval round; the model still chooses tools. Missing patch preconditions fail. |
| Provider phases | Parse completed explicitly labeled finals through supported middleware | Live Responses messages include commentary and final JSON; ProviderStrategy concatenates text. Retain original messages and parse final_answer only, requiring identical content if multiple finals exist. Reject incomplete/conflicting/unmarked output. Revisit when the pinned framework natively handles phases. |
| Source receipts | Return checked binding with source reads | Source access already checks run/revision/hashes. Expose that receipt so alignment does not require a redundant tool call. Unknown deployment remains unknown; foreign identity/revision fails. Configuration/schema remains independently available. |
| Report integrity | Strict provider schema plus one application correction | A post-restart report passed schema but cited a mistyped evidence ID. Preserve the rejected candidate, close retrieval and allow one model correction using existing IDs. Never rewrite IDs automatically or weaken validation. A second rejection or unavailable budget remains incomplete. Revisit only after repeated live evaluation. |
| Final-call constraints | Retrieved evidence-ID enums and checked alignment labels | Prevent mechanically invalid references/availability labels at generation while preserving application checks. No diagnostic text is supplied; valid references still require semantic review. |
| Log retention | Two distinct successful attempt bodies within16 KB | v11 source navigation cleared actual exception logs, leading to false missing-evidence claims. Retain request copies only; complete checkpoints remain untouched. |
| Validation import isolation | Bare Python DAG parse inside the same restricted container | Four behavior checks passed while Airflow import within pytest exited139. Running DAG parsing in a fresh Python process passed the same assertions. The exact native crash cause remains unconfirmed; no resource/network/credential boundary was removed. |
| Windows startup | Docker Linux containers managed from PowerShell | Native Windows Airflow is unsupported. WSL2 without Docker still needs virtualization and its own setup/validation. A script handles user/system Docker paths without changing OS settings. |
